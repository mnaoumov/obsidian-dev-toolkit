# AGENTS.md

## Project overview

`@mnaoumov/obsidian-dev-toolkit` — Tooling for Obsidian plugin development: the plugin builder for esbuild, vite, rollup, webpack and parcel, shared ESLint/Vitest configs, demo vaults and the release script.

It depends on `@mnaoumov/typescript-lib` and `@mnaoumov/typescript-dev-toolkit`, and takes `@mnaoumov/obsidian-lib` as a required peer dependency (`^6.0.0`, since the test setup imports `obsidian-lib-state`, which `6.0.0` introduced; `devDependencies` holds the copy this repository builds and tests with). **It is a peer and not a dependency so that a plugin gets exactly one copy**: with a dependency, a plugin on a major the range did not accept got a second, nested copy, the toolkit's test setup reset that copy, and the plugin's own copy threw `obsidian-dev-utils is already initialized` in every test after the first. When a new `obsidian-lib` major ships, widen the peer range once the toolkit works against it. It is what an Obsidian plugin builds, lints, tests and releases with: the esbuild plugin builder, the Obsidian layer of the shared ESLint config, the shared Vitest config (`defineObsidianPluginVitestConfig`), the plugin release wrapper, the Obsidian test-setup endpoints, the demo-vault helper and the integration-test harness plugin, and `templates/`.

- It is tooling: all of `src/` is linted as scripts, and `obsidianmd/no-nodejs-modules` is off for it. `eslint-plugin-obsidianmd` reads `isDesktopOnly` from a `manifest.json` this repository does not have, so it prints `Failed to load JSON file` on every lint run.
- **Its own scripts import `../src/*.ts`, never the package by name**, as in `@mnaoumov/typescript-dev-toolkit`.
- The ESLint config here is the Obsidian layer over the generic one (`src/linters/eslint-config.ts`): obsidianmd recommended, the Node-builtins exemption for `src/**/desktop-*.ts`, the integration-test rules, `manifest.json` and `LICENSE`. Its own rules are a plugin of their own, registered under `obsidian-dev-toolkit` (`src/linters/eslint-rules/obsidian-dev-toolkit-plugin.ts`), beside the generic rules that `@mnaoumov/typescript-dev-toolkit` registers under `typescript-dev-toolkit`; a disable comment names whichever package owns the rule.
- **Interface and object-type-alias properties are readonly by default**, through `typescript-dev-toolkit/readonly-interface-members` from `@mnaoumov/typescript-dev-toolkit` 4.0.0. Genuine mutable state (build lifecycle flags, scanner state, release-edited manifests and test doubles) keeps a property-level disable with the mutation explained; do not disable the rule for a whole interface or file.
- **Bare keyword bindings use a `$` prefix**, through `typescript-dev-toolkit/no-keyword-identifiers` from `@mnaoumov/typescript-dev-toolkit` 5.0.0. Use `$module` and `$event` for bindings while preserving property names, import/export contracts and generated runtime code; the rule offers scope-aware suggestions rather than autofixes.
- The markdownlint config here is the Obsidian layer too (`src/linters/markdownlint-cli2-config.ts`, `obsidianMarkdownlintCli2Config`): the generic config plus this package's markdownlint rules, and the template re-exports it.
- **One plugin-name list feeds three rules.** `src/linters/plugin-names.ts` holds the display names a plugin's text must mark as code, plus the project's own `manifest.json` `name`; the ESLint rules `plugin-name-as-code` (comments, autofixed) and `plugin-name-as-code-in-ui` (UI strings, reported only) and the markdownlint rule `plugin-name-as-code` all read it. All three are on (`error`) in the shared configs; a consumer passes `{ additionalPluginNames: [...] }` for names the list lacks, and `{ excludedPluginNames: [...] }` to take out a name that is an ordinary word in its text (its own manifest `name` included, as for `Patterns`), which wins over every source. Add a name to the list, never to one rule, and exclude a name per rule rather than turning a rule off, which would stop it checking every other name.
- **In UI, inline code is built with `appendCodeBlock()`, never a bare `<code>`.** Obsidian's app UI (notice, setting name and description, modal, view) gives a bare `<code>` only a monospace font, no inline-code chip; `appendCodeBlock()` from `@mnaoumov/obsidian-lib`'s `html-element.ts` renders `strong.markdown-rendered.code > code`, which gets it. The ESLint rule `no-bare-code-element` reports every `createEl('code', ...)` in shipped source, whatever its text, and `plugin-name-as-code-in-ui` names `appendCodeBlock()` as the fix; a module whose job is to build that element disables the rule on the line with its reason.
- **What the published output imports must be installed for a consumer.** `build:validate-dependencies` (`scripts/build-validate-dependencies.ts`, over `validateDependencies` from `@mnaoumov/typescript-dev-toolkit`) reads every bare specifier of `dist/lib` and `bin/`, declarations included, and fails the build unless it names a `dependencies` or `peerDependencies` entry, the package itself or a Node builtin. `npm install -D` of a new major once moved `@mnaoumov/typescript-dev-toolkit` into `devDependencies`, which nothing in this repository notices, while every consumer's build failed on `Cannot find module`. A type a declaration imports from an optional bundler's package (`@parcel/types`) is an optional peer like the bundler.
- **A module that does not need an optional peer must load without it**, so it imports the peer only as types or through a call-time `import()`. The ESLint layer is the one that matters most, since every plugin lints and not every plugin runs integration tests: `no-over-cap-wait-in-eval-in-obsidian` once imported its cap from `obsidian-integration-testing`, and `linters/eslint-config` threw `Cannot find module` in any project without the harness. The modules whose whole job IS a peer keep a static import of it: `demo-vault-buttons` and `demo-vault-coverage` call vitest's `describe` at collection time, and `test-runners/integration-test-plugin` has to register into the same harness instance the consumer's setup loaded. **Those three are therefore kept off the generated barrels** (`excludeFromIndex` in `scripts/build-generate-index.ts`) and reached only through their own subpaths, because a barrel that re-exported them threw `Cannot find module` without the peer and, under CommonJS, `Vitest cannot be imported in a CommonJS module using require()` even with it; a new module of that kind joins the list. The check is to `npm pack`, install the tarball into an empty project, and `import` / `require` every `dist/lib` module, with ESM and CJS in separate processes.
- `templates/` is copied verbatim into `dist/templates/` (`build:templates`) and type-checked against the built declarations (`build:validate-templates`, `tsconfig.templates.json`); nothing else type-checks it.
- `build:demo-vault-helper` and `build:integration-test-plugin` bundle the two plugins this package ships in `dist/`, from `demo-vault-helper/` and `integration-test-plugin/`. The harness bundle is checked to LOAD under a mobile-shaped `node:vm` context (`scripts/helpers/assert-mobile-loadable-bundle.ts`), since it imports the whole of `@mnaoumov/obsidian-lib`.
- **Every bundler is a thin adapter over one bundler-independent core, `src/bundlers/obsidian-plugin-build.ts`**: the externals, the dist folders, the banner, the `styles.css` merge, `manifest.json` and `.hotreload`; `src/bundlers/obsidian-plugins-folder-deployment.ts` is the vault deployment every development build runs. `esbuild` is the default builder; `vite.ts` and `rollup.ts` are plugins (sharing `rollup-compatible.ts`, typed structurally because vite 8 builds with rolldown), `webpack.ts` is a plugin that fills only the options the consumer left unset, and `parcel.ts` runs parcel's JS API with a `.parcelrc` it generates into `.parcel-cache/obsidian-dev-toolkit/`. **Parcel's two size traps are handled there, and both looked like a missing option rather than a bug:** its `electron-renderer` target resolves with the `node` export condition, so the generated resolver runs `@parcel/node-resolver-core` itself with the browser's conditions (switching the context to `browser` instead would polyfill `process` and `Buffer` and inline the build machine's `process.env`); and a target passed in the options is scope-hoisted, and so tree-shaken, only when `defaultTargetOptions.shouldScopeHoist` says so, whatever `isLibrary` says. Hoisting in turn needs the generated pre-minify optimizer, which blanks the bundle's `require("./styles.css")` and wraps a production bundle in a function so swc may rename its top-level bindings. Measured 2026-10-16 on the feature fixtures: Vue 594 → 88 KB, Svelte 224 → 28, Solid 45 → 9.4. Those four bundlers are optional peer dependencies, so their modules import them only as types (webpack's classes come from `compiler.webpack`, parcel's `@parcel/core` through a dynamic `import()`): the barrels put every module on an esbuild user's load path. The guide is `docs/src/content/docs/guides/bundlers.md`.
- **How a development build is reloaded is the `reload` option every adapter takes (`ObsidianPluginDeploymentOptions`, beside `obsidianConfigFolder`)**: `'hot-reload-plugin'` (the default: the `.hotreload` marker and the owned instance with HotReload), `'obsidian-cli'` (`src/bundlers/obsidian-cli-reload.ts`: `obsidian vault=<vault folder name> plugin:reload id=<manifest id>` in the developer's own Obsidian, falling back to an `eval` that loads the manifests and enables a plugin Obsidian has not seen yet), or `false`. **The Obsidian CLI exits 0 on failure**, printing `Vault not found.` or `Error: ...`, so the module reads the output; measured against Obsidian 1.14.4 on 2026-10-16. **`obsidian-integration-testing` is an optional peer, so the deployment `import()`s it only when `'hot-reload-plugin'` runs**: every adapter imports the deployment module, and a static import made every adapter fail to load in a project without it.
- **esbuild's `ignoreListSources` extends the shared source-map ignore list**, covering `typescript-lib`'s `debug`, `monkey-around` and `obsidian-lib`'s `MonkeyAroundComponent`; `false` disables it. `esbuild-impl/ignore-list-source-map-plugin.ts` runs after custom plugins and the development URL fix, before vault deployment. It preserves full development and explicitly requested external maps and existing ignore entries; otherwise it emits a compact inline production map containing only ignored regions, collapsed to one source. Its trailing `/* nosourcemap */` keeps Obsidian from stripping that map outside debug mode. Only its temporary JavaScript and CSS maps are removed. The guide is `docs/src/content/docs/guides/bundlers.md`.
- **The Jest counterpart of the vitest config is `defineObsidianPluginJestConfig` (`src/test-runners/jest-config.ts`)**, over `defineJestConfig` from `@mnaoumov/typescript-dev-toolkit`: `jsdom`, `obsidian` mapped onto the mocks, and the two setup files in `setupFilesAfterEnv` (not `setupFiles`, since `jest-setup.ts` registers hooks). `jest`, `ts-jest` and `jest-environment-jsdom` are optional peers; a plugin runs it through `test-runners/auto` there. `jest-config.integration.test.ts` runs a real Jest on a fixture plugin, swapping this package's own setup-file specifier for `src/jest-setup.ts`, because Jest checks that a setup file resolves before it reads `moduleNameMapper`.
- **The end-to-end runners beside obsidian-integration-testing live in `src/test-runners/`**: `wdio-obsidian.ts` (`defineWdioObsidianConfig`, typed structurally so the toolkit takes no WebdriverIO dependency, and `testEndToEndWithWdioObsidian`) and `obsidian-test-runner.ts` (`testEndToEndWithObsidianTest`), sharing `e2e-runner-support.ts`. The guide is `docs/src/content/docs/guides/e2e-testing.md`. `obsidian-test` 0.1.2 cannot run on Windows (its dynamic-runner `resolveId` compares a `/`-separated suffix against a `\` path), so only its command line is unit-tested here.
- **A plugin's CI and release are reusable workflows this repository ships, not files a plugin carries**: `.github/workflows/obsidian-plugin-ci.yml` (install, gate, and the opt-in coverage badge pushed to a `badges` branch), `obsidian-plugin-release.yml` (from a pushed tag: tag-is-manifest-version check, build, `archive-demo-vault`, `gh release create`, `actions/attest`) and `obsidian-plugin-attest-release-assets.yml`. Callers pin them to a release tag (`@3.0.0`), so **renaming one, or removing an input, breaks every caller on its next bump**. The CI and release ones share their `Resolve settings` and setup steps verbatim, and every shell step is written against environment variables only, so `scripts/github-workflows.test.ts` can run it under bash (Git's bash on Windows) with `gh` faked and the badge pushed to a local repository; keep both true. The commands they run are the package's two bins, `generate-coverage-badge` (`src/test-runners/coverage-badge*.ts`) and `archive-demo-vault` (`src/demo-vault-cli.ts`), in `bin/` over the built `dist/`. The guide is `docs/src/content/docs/guides/ci-and-release.md`. `actionlint` is not a dependency; run it by hand with `go run github.com/rhysd/actionlint/cmd/actionlint@latest`.
- **The build features (`framework`, `styles`, `wasm`) are one option set every adapter takes, compiled by one set of transforms.** `src/bundlers/obsidian-plugin-features.ts` holds the options, the framework defines, the file-kind dispatch and the optional-peer loader, which resolves each feature's packages from the PROJECT's `node_modules` and names the `npm install` line when one is missing. `src/bundlers/obsidian-plugin-transforms.ts` holds the transforms (Solid through Babel, Svelte through the project's `svelte/compiler`, React/Preact JSX, PostCSS with Tailwind and CSS modules, `.wasm` as bytes). esbuild, rollup and vite call them in-process (`esbuild-impl/feature-options.ts`, `rollup-compatible-features.ts`); webpack through `obsidian-plugin-webpack-loader.ts`, which the adapter names by path; parcel through a transformer it generates that `import()`s both modules by URL. **That is why both modules, and the loader, are ERASABLE TypeScript only** (no enums, no parameter properties): from source, webpack and parcel's workers load them through Node's type stripping, which is how the integration test exercises them. Vue is the exception that uses `unplugin-vue` per bundler (parcel: `@parcel/transformer-vue`). **The optional `@babel/core` peer admits Babel 8 (`^7.29.7 || ^8.0.0`) although the `solid` path needs Babel 7**: `babel-preset-solid` declares `@babel/core` `^7.0.0` itself, so npm already holds every Solid user to 7, while a `^7`-only peer here refused the whole tree of a consumer that ships Babel 8 for its own reasons and never compiles Solid (`obsidian-codescript-toolkit`, 2026-10-21). Narrow it again only if this package starts calling Babel outside the `solid` path. The tsconfig presets (`tsconfig/*.json`) and ambient types (`types/*.d.ts`) ship outside `src/`, so `scripts/build-generate-exports.ts` passes their `exports` entries to `generateLibraryExports` as `additionalExports`.
- **`npm run test:integration` builds `test-fixtures/obsidian-plugin` with every bundler and loads each `main.js` the way Obsidian's loader does** (`function (require, module, exports)` with a bare `module` that has no `require`, which is what broke parcel's runtime until the generated optimizer handed it one). It builds a temporary copy of the fixture, because every adapter takes the nearest `package.json` for the project root and `build:clean` deletes every nested `package.json` in the repository; so the fixture's is `fixture-package.json`, renamed in the copy. Each folder of `test-fixtures/features/` is laid over that copy and built with every bundler too, then run in a jsdom context so its component renders; the copy sits at its REAL path, since webpack's virtual modules (which `unplugin-vue` uses) miss a module whose path runs through a junction. CI runs it after the gate. The copy and the build are `scripts/helpers/bundler-fixture.ts`, shared with the suite below.
- **`npm run test:integration:obsidian` loads the same eight builds in a REAL Obsidian** (`src/bundlers/bundlers.obsidian.integration.test.ts`, project `obsidian-integration-tests`): an owned instance with an empty vault (`vitest-global-setup-no-plugin`), each build installed under its own plugin id and enabled, then its command run (returning the real `path.sep` through Electron's `require`), its `styles.css` applied, and both gone once it is disabled. **CI does not run it, because the runner has no Obsidian**, so run it by hand after touching an adapter or the build core. **The project is deliberately NOT named `integration-tests:obsidian`**: `test:integration` selects `--project=integration-tests:*`, so that name would put it in CI's run. **`npm run test:integration:obsidian:android` runs the same file on Obsidian Mobile** (project `obsidian-android-integration-tests`, Appium transport, AVD `obsidian_test`; not `obsidian-integration-tests:android`, since `test()` from `typescript-dev-toolkit` also selects `<name>:*` and the desktop script would then boot the emulator too), which is what the `node:vm` model cannot stand in for. The suite reads the platform from `inject('obsidianTransport')` and asserts `app.isMobile` against it. On mobile it does not run the command, because mobile has no Node builtins, so the fixture's `sep` is missing there: esbuild's interop reads it as `undefined`, and the other seven builds throw `Cannot read properties of undefined (reading 'sep')`. All eight load, register the command and apply and drop `styles.css` (measured 2026-10-16). `inject` is typed through `obsidian-integration-testing/vitest/typings` in `tsconfig.json`'s `types`, because that module has no export, and lint's autofix deletes an empty `import type {}` of it.
- The unit tests load `@mnaoumov/typescript-dev-toolkit` and `@mnaoumov/typescript-lib` through Vite (`server.deps.inline`), so a test's `vi.mock` of `node:fs` reaches the toolkit helpers the code under test calls.
- Vitest honors `BULK_CORES` as its worker cap when bulk work sets it; the type-aware ESLint project retains its single worker.

## Commands

Every script is a thin entry point under `scripts/`, run with `jiti`, over the shared tooling in `@mnaoumov/typescript-dev-toolkit` (and `@mnaoumov/obsidian-dev-toolkit` for an Obsidian package).

- `npm run gate` — **the branch gate: run it before committing.** It is the same code `npm run version` runs as its release preflight: the lockfile check, `format:check`, `spellcheck`, `lint:md`, `build`, `lint`, `find-overexposed`, `test:coverage`. `npm run gate -- --no-build` skips the build when the output is current. CI (`.github/workflows/ci.yml`) runs the whole gate.
- `npm run build` — every `build:*` step this package defines, in order (`scripts/build.ts`).
- `npm test` / `npm run test:coverage` / `npm run test:watch` — the unit tests; `test:coverage` holds all four thresholds at 100%.
- `npm run test:integration` — builds the fixture plugin with every bundler adapter and loads each result as Obsidian would (`npm run gate '--' --integration` includes it).
- `npm run test:integration:obsidian` — loads the same builds in a real desktop Obsidian through `obsidian-integration-testing`; local only, since CI has no Obsidian.
- `npm run test:integration:obsidian:android` — the same suite in Obsidian Mobile on the `obsidian_test` AVD, through the Appium transport (project `obsidian-android-integration-tests`; the harness starts Appium and the emulator). Local only, and one Android run at a time on the machine.
- `npm run lint` / `npm run lint:fix` — ESLint. A warning fails it. ESLint is type-aware and reads the generated barrels, so build first on a fresh clone.
- `npm run lint:md` / `npm run lint:md:fix`, `npm run format` / `npm run format:check`, `npm run spellcheck` — markdownlint (with the soft-break rule on: every paragraph is one physical line), dprint and cspell.
- `npm run docs:build` / `npm run docs:dev` / `npm run docs:preview` — this package's documentation site, built with `@mnaoumov/typescript-dev-toolkit`'s docs-site builder (`scripts/docs-site-config.ts`, `astro.config.ts`, `docs/`): the API reference generated into `docs/src/content/docs/api`, the Open Graph cards, `astro build` into `docs/dist`, then a check of every link of the output, external ones included. `.github/workflows/build-pages.yml` builds and deploys it to `https://mnaoumov.dev/obsidian-dev-toolkit/` on every published release. Its pages link into the sites of `typescript-lib`, `typescript-dev-toolkit`, `typescript-test-toolkit` and `obsidian-lib`, so those deploy first. The guides moved here from `obsidian-dev-utils`. `src/docs-site/obsidian-external-type-links.ts` (`OBSIDIAN_EXTERNAL_TYPE_LINKS`) is the Obsidian layer of the builder's `externalTypeLinks`, the CodeMirror and Moment types an Obsidian package's API names. This site takes it from `../src/`, and `obsidian-lib`'s site is meant to import it once a release carries it, in place of its own copy of the same ten entries.
- `npm run docs:check-snippets` — type-checks every fenced `ts` / `js` block of the guides against `src/` (`scripts/helpers/docs-snippets.ts`), mapping this package's own name onto `src/` for the check alone. The gate runs the same check as `scripts/helpers/docs-snippets.test.ts` in the `unit-tests:scripts` project, beside `outdated-references.test.ts`, which fails on a retired `obsidian-dev-utils` module path, import, repository link, console recipe, or old demo-vault directive / frontmatter spelling (now `obsidian-dev-toolkit-disable…` and `obsidian-dev-toolkit:`, which `demo-vault-coverage` itself also reports in a consumer's vault) in the README, this file, the guides, the sources, the scripts, the two shipped plugins and `templates/`. It also fails on the wire names renamed with `@mnaoumov/obsidian-lib` `6.0.0`: the `__obsidianDevUtils` bag (now `globalThis.__obsidianLib`), the `obsidian-dev-utils-state` module (now `obsidian-lib-state`) and the harness global `window.__obsidianDevUtilsModule` (now `window.__obsidianLibModule`). The bare name stays legal. An HTML comment above a fence shapes its check: `<!-- snippet-check: context <declarations> -->` declares names the prose already introduced, and `<!-- snippet-check: skip <reason> -->` exempts a snippet that cannot compile here, such as one needing a package a plugin installs and this repository does not. A line that names an old address on purpose carries `outdated-reference-ok`. Both helpers are copies of `typescript-test-toolkit`'s, until `@mnaoumov/typescript-dev-toolkit` ships them.
- `npm run commit` — a guided Conventional-Commits message.
- `npm run version '--' <type> [--no-changelog-editing]` — the release. Quote the `--` in PowerShell.

## Standalone layout

This package moved out of the `obsidian-dev-utils` workspace, with its history, on 2026-10-15. Five things differ from the workspace and are easy to undo by accident:

- **A sibling `@mnaoumov/*` package is an ordinary dependency, installed from npm.** There is no `@mnaoumov/source` export condition any more: `generateLibraryExports` writes none unless asked, and `package.json`'s dependencies are the package boundary the workspace's ESLint config used to enforce.
- **A package cannot install itself, so its own scripts never import it by name.** In the tooling packages the scripts import `../src/*.ts`, so the toolkit builds and lints itself from its sources.
- **A test-support package that depends on this one would otherwise bring a SECOND copy of it into a test run.** Where that happens (`typescript-lib`, `obsidian-lib`), `scripts/vitest-self-source.ts` resolves this package's own name onto `src/`, the test-support packages are listed in the vitest projects' `server.deps.inline` so their imports go through it, and `tsconfig.json`'s `paths` does the same for the types. Drop any of the three and a test-setup reset reaches a different module instance than the code under test.
- **A package a test mocks through must be processed by Vite.** A dependency Node loads directly ignores `vi.mock` and survives `vi.resetModules()`, so a test that mocks `node:fs` underneath a toolkit helper, or that loads a second copy of a module on purpose, needs that dependency in `server.deps.inline`.
- **The first `package-lock.json` was seeded from the workspace lock**, so every dependency starts at the version the workspace tested rather than at whatever each range resolves to today.

## Releasing

`npm run version '--' <patch|minor|major>` runs the gate, bumps the version, writes `CHANGELOG.md`, commits, tags, pushes and creates the GitHub release. The release carries no assets. Publishing the release triggers `.github/workflows/publish-npm.yml`, which rebuilds and runs `npm publish` through npm trusted publishing (OIDC): no npm token exists anywhere, and a publish from a developer machine is not possible. The package's trusted publisher on npmjs.com names this repository and `publish-npm.yml`; renaming the workflow breaks publishing until that setting matches.

`1.0.0` was published once from the `obsidian-dev-utils` workspace, all five packages together, because each package's tooling depends on siblings that were not on npm yet. This repository releases from `1.0.1` on; the `1.0.0` tag marks where it took over.

Conventional Commits, enforced by commitlint in the `commit-msg` hook, which also refuses a header the spellchecker rejects. The `pre-commit` hook runs nano-staged: spellcheck, `lint:fix`, `format` and `lint:md:fix` on the staged files. Set `NANO_STAGED=0` in a gitignored `.env` to skip it.

## Carried over from obsidian-dev-utils

These sections were written in the `obsidian-dev-utils` workspace, where this package lived until it moved here with its history, and they still govern it. "This repository" or "this library" in them means that workspace; a path of another package is written `mnaoumov/<package>:<path>`, the file in that package's own repository.

### File Structure

Every source file follows this pattern:

```typescript
/**
 * @file
 *
 * Brief description of module purpose.
 */

import type { SomeType } from './some-module.ts';

import { something } from './other-module.ts';

export function myFunction(param: Type): ReturnType {
  // ...
}
```

### Naming

- Directories: kebab-case (e.g., `script-utils/bundlers/esbuild-impl`, `test-runners`)
- **Exception:** `constructors/` files use camelCase matching the exported function name (e.g., `getDomEventsHandlersConstructor.ts`), mirroring the `obsidian-typings` Constructors convention
- **An `Async` suffix disambiguates, it does NOT mean "this returns a promise".** Add it only when a synchronous counterpart of the same name already exists and would otherwise collide. Being `async` is never on its own a reason for the suffix — measured 2026-07-31, ~18 suffixed members against ~179 async members without one, and **every** established use resolves a name collision: `onloadAsync` (Obsidian's `onload`), `hideAsync`, `triggerAsync`/`tryTriggerAsync`, `createDivAsync`/`createElAsync`/… (Obsidian's sync `createDiv`/`createEl`), `setTimeoutAsync`/`requestAnimationFrameAsync`/`setImmediateAsync`/ `nextTickAsync` (the callback-based globals), `replaceAllAsync` (`String.replaceAll`), `noopAsync` (`noop`). (`invokeAsyncSafely` is not a counter-example — its `Async` is mid-name, describing what it invokes.) A `*Params` interface is named after its method, so it follows the method either way.

### Documentation

- Every exported function/class requires JSDoc with `@param` and `@returns` tags
- Every file requires a `@file` JSDoc comment at the top
- Test files and mock files are exempt from documentation requirements

### Imports

- Sorted alphabetically (enforced by `eslint-plugin-perfectionist`)
- Always include `.ts` extension in relative imports

### Build

- esbuild for bundling (ESM + CJS dual output)
- `src/**/index.ts` files are auto-generated — do NOT edit them manually
- `package.json` exports are auto-generated via `build:generate-exports`
- `mnaoumov/obsidian-lib:src/__merged.ts` is an auto-generated flat re-export barrel of every renderer-safe **value** export (gitignored + eslint-ignored, exactly like `index.ts`; produced by `build:generate-merged`, which runs before `build:generate-index`). It backs the `__merged` namespace of the `@mnaoumov/obsidian-lib` root export and the `lib` bag injected into `evalInObsidian` closures — wired via `registerLibResolver` in `scripts/integration-test-obsidian-setup.ts` plus the `Lib` augmentation in `mnaoumov/obsidian-lib:src/@types/obsidian-integration-testing.d.ts`. The generator **fails the build if two modules export the same value name**: every public value export must be unique (this is why `path.ts` / `string.ts` `normalize` were renamed to `normalizePath` / `normalizeString`). Do NOT edit `__merged.ts` manually.
- **The integration-test harness plugin bundle is checked at build time for whether it can load on mobile.** `buildIntegrationTestPlugin` runs `assertMobileLoadableBundle` (`scripts/helpers/assert-mobile-loadable-bundle.ts`), which evaluates the emitted `main.js` in a `node:vm` context shaped like Obsidian mobile — `require` returns `undefined` for every Node builtin and a permissive stand-in for the app-provided externals, and `process` is present and renderer-shaped so a load-time branch (as in `debug`) takes the browser path a webview does. It asserts only that module INITIALIZATION survives, so L6's call-time dynamic `import()` of platform-only work still passes. It guards both outputs (`dist/integration-test-plugin/`, which ships, and `dist/dev/`), because that bundle is seeded into an Android integration vault, where a load-time reach for a platform-only API surfaces as an opaque "plugin failed to load" with every test in the project failing behind it.
- **That one check covers the whole library, which is why L5 can allow the barrels to re-export every module.** The harness plugin's entry imports `../src/index.ts` — the entire public surface — so its bundle is the worst-case consumer: a plugin that imports everything. Any module that stops being import-safe on mobile fails `npm run build` here, long before it reaches a phone. Do not weaken that entry to a narrower import; it is what makes the check load-bearing rather than incidental.

### L5. Platform-only modules carry a `desktop-` / `mobile-` filename prefix

- A module that only works on (or is only meant for) **desktop** must have a `desktop-` filename prefix; a **mobile**-only module must have a `mobile-` prefix. The prefix marks the file, not its exports — e.g. `desktop-trusted-input.ts` exports `typeIntoEditor`, not `desktopTypeIntoEditor`.
- **The `desktop-` prefix is LOAD-BEARING, not advisory** — `getNodeBuiltinsConfigs` in `src/linters/eslint-config.ts` keys the Node-builtins exemption off `src/**/desktop-*.ts`, in every plugin built on this library. A desktop-only module that skips the prefix keeps reporting `import-x/no-nodejs-modules` **and** `obsidianmd/no-nodejs-modules`, the second of which a consumer cannot waive (the community-directory runner turns an inline `obsidianmd/*` disable into an error); a cross-platform module that wrongly takes the prefix gets an exemption it should not have. The exemption exists because the `Platform.isDesktopApp` gate lives one file up, in the caller, where neither rule can see it — see **L6**.
- **Tests group by SUT, so they take a dot segment, never the prefix.** A desktop-only test of a cross-platform SUT is `<sut>.desktop.test.ts` / `<sut>.desktop.integration.test.ts` — the subject first, the platform as a dot segment, matching `*.android.integration.test.ts`. A desktop-only module's own co-located test just inherits the module's name (`desktop-zip-extractor.test.ts`), so it is already grouped and already exempt. Both shapes are covered without a further glob: every `*.integration.test.ts` and every `context.testFiles` unit test is exempt from the Node-builtins bans anyway, since neither is ever bundled into `main.js`.
- "Platform-only" means the module directly uses a platform-restricted API (Node builtins, `window.electron`, mobile-only APIs) at the **top level** (so importing the module loads that API). Examples: `desktop-trusted-input.ts` (`window.electron` trusted input), `desktop-demo-vault-opener.ts` (`node:fs`/`node:os` + `window.electron`). A module using only cross-platform APIs at the top level gets no prefix — e.g. `community-plugins.ts` (uses `requestUrl`), and `open-demo-vault-command-handler.ts`, which is desktop-*gated* but stays cross-platform-loadable by dynamic-importing the desktop-only opener (see **L6**).
- **The prefix restricts where a module may be CALLED, never whether it may be IMPORTED — every module in `src/` must survive being imported on either platform.** The generated barrels (`src/**/index.ts`, `mnaoumov/obsidian-lib:src/__merged.ts`) re-export **every** leaf they find, and `src/index.ts` pulls in both, so anything under `src/` is on the load path of every consumer that imports a namespace — and of the integration-test harness plugin, which loads the whole library on a phone. A `desktop-` name therefore buys no exemption from being loaded there; it only says "calling this on mobile is a bug". `desktop-trusted-input.ts` is the model: it names `window.electron` only *inside* its functions, so importing it on mobile is inert.
- **So a platform-only dependency that runs code while INITIALIZING must be dynamically imported.** A static `import { existsSync } from 'node:fs'` is fine (mobile's `require` returns `undefined` and nothing reads it at load time), but a dependency whose own top level *evaluates* a platform-only API is not. `adm-zip` opens with `const { randomFillSync } = require('crypto')`, so a static `import AdmZip from 'adm-zip'` in `desktop-demo-vault-opener.ts` threw during barrel initialization and killed the harness plugin's load on Android — every test in its `integration-tests:android` project failed behind an opaque "plugin failed to load". `adm-zip` has since left this package entirely, so neither half of it is in the tree to inspect: extraction moved to `desktop-zip-extractor.ts`, which needs only `node:zlib`, and the release-time archiver moved to `fflate`. The rule stands for the next such dependency — defer it behind a call-time `import()`, or do without it.
- **A dependency on the plugin-runtime path costs every consumer's bundle, and a dynamic `import()` does NOT buy it back.** An Obsidian plugin ships one CJS `main.js`, esbuild has no code splitting to put a chunk behind, and `await import()` only defers EVALUATION — the module body is inlined either way. Measured 2026-08-31 in `obsidian-fix-tab-size`'s 247 KB bundle: the demo-vault opener and the `adm-zip` it then imported took ~41 KB of it, ~17%, in a plugin that opens no archives of its own. Prefer a Node builtin (already `external`, so free) over a dependency for anything reachable from `mnaoumov/obsidian-lib:src/`.
- `mobile-trusted-input.ts` is the `mobile-` example: it reads `window.__obsidianIntegrationTesting`, a global only the integration-testing harness installs, and calling it anywhere else throws. Like its `desktop-` twin it names that global only *inside* its functions, so importing it on desktop is inert — which it has to be, since the barrels put it on every consumer's load path.
- (the naming half is enforced only in the negative — a non-`desktop-` file using `node:` reports, since it gets no exemption, but a `desktop-` file that uses nothing platform-only is not flagged for taking a prefix it does not need. A custom check could still flag `window.electron` usage in a non-`desktop-` file, which no rule covers. The **import-safety** half IS enforced, by the mobile-load check on the harness plugin bundle described under **Build** — that bundle imports the entire library, so it stands in for the worst-case consumer.)

### L15. A function serialized into the emitted banner may only reference its own module — and `globalThis` stays spelled out

- `preprocess-plugin.ts` ships code as **text**: `makePreprocessBanner()` (`mnaoumov/typescript-dev-toolkit:src/bundlers/esbuild-impl/preprocess-plugin.ts`) builds the esbuild banner out of `String(fn)`, so what lands in every consumer's bundle is source text, not a linked module. Two consequences that no type-check or unit test catches, because both are correct in the builder process and wrong only in the emitted artifact:
- **Cross-module calls do not survive.** esbuild compiles an imported call to `(0, import_module.fn)(…)` in the CJS dist — `makeValidVariableName` appears exactly that way in `dist/lib/cjs/script-utils/bundlers/esbuild-impl/preprocess-plugin.cjs` — naming a binding the emitted bundle does not have. Only **same-module** references stay bare identifiers. That is why `ensureBrowserProcess` / `keepName` live beside `initCjs` / `initEsm` rather than in a tidy `banner-shims.ts` (drafted once, then deleted for this reason), and why `makePreprocessBanner()` serializes the shims alongside the `init` function that calls them.
- **The two packages split the banner along that line, and the split is why each half is self-contained.** The generic plugin in `typescript-dev-toolkit` owns the shims, `initCjs` / `initEsm` and the shared IIFE. The Obsidian plugin in `obsidian-dev-toolkit` (same file name) calls it with `additionalBannerInitFunctions: [patchObsidianRequire]` for CommonJS and an `activeWindow`-reading `cjsImportMetaUrlProvider`, and each of those is serialized as its OWN `(fn)()` after the shared scope. So `patchObsidianRequire` cannot call `ensureDisposeSymbols` or `extractDefault` from the generic module (it would compile to `(0, import_preprocess_plugin.extractDefault)` in `obsidian-dev-toolkit`'s CJS build) and carries its own `extractDefault`. The generic CJS banner has no `require` patch, so the three `typescript-*` packages' CommonJS output loads under plain Node, where the patch's `globalThis.app.isMobile` read used to throw on the first non-built-in `require`. **This package's own `dist/lib` is built with the generic plugin too** (`scripts/build-lib.ts`): it is Node tooling and nothing in it runs inside Obsidian, so with the Obsidian banner every `.cjs` module threw on load. The patch itself now reads `app` optionally and treats a host without one as desktop, because `obsidian-lib`'s `dist/lib` still carries it and is loaded by Node test runners.
- **A helper that is referenced but not serialized fails silently**, degrading to whatever the consumer's global scope holds under that name. `globalThisRecord['__name'] ??= name;` shipped for years resolving `name` to `window.name` — a string, not a function. Nothing threw, because nothing called it.
- **Never let `lint:fix` shorten `globalThis.x` to `x` in banner code.** `unicorn/no-unnecessary-global-this` autofixes `globalThis.process` → `process`, which is equivalent in a module but not in the banner: there a bare `process` is a free identifier, so reading it where the host has none throws a **ReferenceError** — precisely the case `ensureBrowserProcess` exists to handle. The line carries a disable comment saying so; keep it.
- **Verify against the built `dist`, never only the source.** Run `npm run build`, then execute the banner sliced out of `dist/lib/cjs/*.cjs` and `dist/lib/esm/*.mjs` against the host shapes you care about. The unit tests call `String(fn)` on vitest's transform, which is exactly the compilation step that differs.
- **The banner is also where `Symbol.dispose` / `Symbol.asyncDispose` get their fallback (`ensureDisposeSymbols`), and it has to stay there rather than beside each disposable.** A disposable keys its method with the literal `[Symbol.dispose]`, while esbuild lowers every `using` to a lookup through its `__knownSymbol('dispose')` helper, which falls back to `Symbol.for('Symbol.dispose')`. On an engine without the well-known symbol the literal key is `undefined`, the method lands under the string `"undefined"`, and every `using` throws `Object not disposable` — which is how a link conversion threw on iPadOS while working on desktop. Filling the slot with the registry symbol, once, before any module body runs, makes both sides agree for every producer at once. `preprocess-plugin.test.ts` pins it end to end: it bundles disposables declared in the shape of `typescript-lib`'s `CallbackDisposable` / `AsyncCallbackDisposable` (not the library's own, whose built copy already carries the banner, so the control below could never fail) and runs them in a `node:vm` context whose `Symbol` lacks both symbols, with a no-banner case that must still throw, so the simulated engine cannot quietly stop simulating anything.
- (cannot be forced by ESLint — a custom rule could flag imported identifiers inside the serialized functions, but not the `globalThis` autofix interaction)

### L16. A notice is transient by design — record it as it arrives, never sample the DOM for it

- `PluginNoticeComponent.showNotice` defaults to `PluginNoticeMode.Replace`, which calls `this.notice?.hide()` before showing the new one: **the next notice from the same component removes the previous one from the DOM.** So a test that reads `activeDocument.querySelectorAll('.obsidian-dev-utils.plugin-notice-content')` (the class `@mnaoumov/obsidian-lib` emits since `6.0.0`; follow it if that library renames it) is not asking "was this notice shown?" — it is asking "is it *still* the newest notice at this instant?", and any follow-up notice makes that false.
- Two mechanisms turn that into an unwinnable race. The rescue notice in `didRescueStillUsedAttachment` is followed by the `updatedLinks` notice the `RenameHandler` defers through `addToQueue`, which takes the same slot; and the harness's `waitUntil` **polls immediately**, so a predicate whose condition is already met exits on the first poll and a latch riding along in that predicate never gets a second look.
- **The tell is inverted timing: it fails when the run is FAST and passes under load.** `waitUntil` returns instantly when the machine is idle, so the loop never runs; a loaded machine spreads the queue out and a poll happens to land while the notice is still up. That is the opposite of a normal flake, which is why running the whole suite is not a valid check — the bug hides there. Run the file ALONE (`npx vitest run --project=obsidian-integration-tests <file>`) to reproduce it.
- **The fix is a `MutationObserver` installed before the action**, accumulating the text of every `.obsidian-dev-utils.plugin-notice-content` element as it is inserted (test the added node and sweep its subtree — the content element rides inside the `.notice` container that is what actually gets added). Do not seed it with a sweep of the existing DOM: a notice left over from an earlier case would then satisfy this one. Assert on the recording, and put both conditions in the same `waitUntil` predicate rather than reading one after the other.
- **Size an in-vault `waitUntil` to fail INSIDE the harness's 30 s `Runtime.evaluate` ceiling.** A 30 s wait can never report: the CDP command is killed first, and vitest's own 30 s `testTimeout` fires at the same moment — so the message naming the unmet condition is replaced by a bare "Test timed out"/"CDP command timed out". The rescue cases use 12 s for this reason. Raising the vitest timeout does not help; the CDP ceiling is the binding one.
  - **This is now ENFORCED, not remembered: `obsidian-dev-toolkit/no-over-cap-wait-in-eval-in-obsidian`.** It sums the declared `waitUntil` / `sleep` budget inside every `evalInObsidian` / `pollInObsidian` closure — counting the 5 s a `waitUntil` takes when it omits `timeoutInMilliseconds`, and resolving an identifier through scope, including one threaded via the call's own `input` — and reports at or over `capInMilliseconds`, which defaults to `DEFAULT_EVAL_CAP_IN_MILLISECONDS` (`30_000`). That constant is restated in `src/test-runners/performance-eval-cap.ts` rather than imported from `obsidian-integration-testing`, because the harness is an optional peer and the import made the shared ESLint config fail to load without it; `performance-eval-cap.test.ts` pins it to the harness's own constant, so the rule still cannot drift from the cap it predicts. **A `*.desktop-performance.integration.test.ts` defaults higher, to `PERFORMANCE_EVAL_CAP_IN_MILLISECONDS` (600 000)**, the per-eval cap `defineObsidianPluginVitestConfig` gives that project's CDP transport; both read it from `src/test-runners/performance-eval-cap.ts`, which exists so the rule does not load `vitest/config` at lint time. That raise is a budget because a perf suite's measurement is one long in-page evaluation that runs on no other project. A repo's own raised desktop `commandTimeoutInMilliseconds` is deliberately NOT read: it is a backstop, not a budget a closure may spend, and the rule enforcing 30 000 against it is the point. It is enabled on ALL files, not only integration tests, because script code that drives a real Obsidian is under the same cap. A budget it cannot resolve statically is silently ignored, so it under-reports rather than crying wolf; a site that genuinely cannot become a `poll` / `until` pair disables it with a written reason. A note is what let this reach thirty repos, which is why it is a rule.
  - **A LOOP declares a ceiling too, and reading it uncovered 18 over-cap closures nothing had ever reported.** A deadline loop — `const deadline = Date.now() + BUDGET` guarded by `Date.now() < deadline`, on either clock — is charged `BUDGET` once, and a counting `for (let attempt = 0; attempt < ATTEMPTS; attempt++)` multiplies the waits inside it by `ATTEMPTS`. Either ceiling counts when it is one conjunct of a compound test, which is how both are written in practice. A `while (true)`, a `for…of`, and a bound that does not resolve all keep the old per-iteration charge rather than a guess.
  - **A HELPER declared inside the closure is charged once per CALL SITE, which took the workspace roster from 95 closures to 138.** Its own waits are summed once and multiplied by the calls that reach it, each call carrying the counting loops it is itself written inside — so a local `waitUntil(check)` of `for (attempt < 40) await sleep(250)` called three times declares 30 000 ms rather than 10 000. A helper declared OUTSIDE the closure stays out of scope, since reading it needs analysis across call boundaries. Recursion terminates by charging a re-entered helper nothing, and a helper no call site reaches keeps the flat single charge the old lexical attribution gave it, so nothing that was reported before this went quiet. **What this does NOT fix is a BRANCHY helper**: an `if` / `else` is summed lexically like two sibling waits, so both arms are charged at every call site — a helper whose two directions wait differently is better written as two helpers, which is what `syntax-highlighting-component.obsidian.integration.test.ts` does and says.
  - **A closure DELIBERATELY left under the cap says so, on one exact line, and the rule's own file-doc comment is where that convention is written down.** The line is `Under the transport's ~30s per-closure cap, not at it.` opening a comment, followed by what that closure's budget is made of and why it stays; inside the closure it speaks for that closure alone, at module scope for every closure in the file. It exists because the rule is SILENT on anything under the cap, so without it a sweep run with a lower `capInMilliseconds` — the cheap way to enumerate the closures sitting just under it — cannot tell a budget somebody read and kept from one nobody has looked at, and re-opens the same decisions every time. Sixty closures across the workspace carried the line as prose before it was written down; it is now the marker such a sweep subtracts, which is what lets one finish. **Being under the cap is not a defect to clear**: "read, and left as it is" is a correct outcome, and tightening a ceiling to bring a number down is how a suite starts failing legitimately on a cold phone. **Blame a ceiling before sizing it** — `git log -L <line>,<line>:<file>` routinely names a commit that chose that number to stop a flake.
  - **So SIZE a shared ceiling against the CALL COUNT, not against the `waitUntil` calls you can see.** That is the practical consequence, and getting it wrong is not hypothetical: a careful sizing pass in a sibling repo left a comment reading "two waits share this one budget" beside a helper the rule now reads as running six times.
  - **The fix for a wait that genuinely needs longer than the cap is `pollInObsidian`, not a bigger number**: a short DOM-reading `poll` closure, `until` evaluated in Node, and the long budget in `timeoutInMilliseconds`. `demo-vault-helper.obsidian.integration.test.ts` has three worked examples.
- Prove the assertion is not vacuous with a **negative control**: comment out the `showNotice` call and confirm the case fails on the wait's own message.
- **When the test OWNS the notice component, record at the source instead — a `MutationObserver` is the fallback, not the goal.** The observer exists because the rescue cases assert on notices raised by production code they do not own. A test that constructs its own `PluginNoticeComponent` can subclass it and push each `showNotice` message into an array, which is both exact and *structurally* immune to neighbors: an observer on `activeDocument.body` still sees a notice any other file raises during its window, while nothing can push into a private array. `path-settings.obsidian.integration.test.ts` does this, and also had to wire its own `AsyncErrorHandlerComponent` — the pooled instance's harness plugin extends plain `Plugin`, not `PluginBase`, so **no unhandled-error notice is rendered there unless the test renders it**. A "no notice was shown" assertion in that instance is vacuous until it owns that wiring; the negative control above is what catches it.
- (cannot be forced by ESLint — a rule could flag `querySelectorAll('…plugin-notice-content')` inside an `evalInObsidian` closure, but not the timing judgment)

### Framework

- Vitest with explicit imports (globals: false) — always import `describe`, `it`, `expect`, etc. from `'vitest'`
- Test environment: `node` by default; use `// @vitest-environment jsdom` directive for browser tests
- Coverage provider: v8
- **`unit-tests:obsidian` runs on `pool: 'vmThreads'`, and the one thing that costs is `vi.stubGlobal('window' | 'document', …)`, which throws there.** The pool builds the jsdom once per worker instead of once per test file — measured 2026-09-15 at `test:coverage` 149.79 s → 56.88 s and that project alone 36.06 s → 9.92 s, since Vitest's own advisory had 67% of tracked time going on jsdom construction. Isolation is unaffected (probed directly: no DOM, `globalThis` or prototype state crosses files in one worker) and so is coverage (`coverage/lcov.info` byte-identical to the default pool's over a six-file subset). But a VM context's `window` and `document` are **non-configurable accessors** on its global, so `vi.stubGlobal` fails with `Cannot redefine property: window` — JS semantics, not something to route around. Every other global (`FileReader`, `Image`, `getComputedStyle`, `fetch`, `electron`) stubs normally. A test that needs to stub one of those two goes in `GLOBAL_STUB_TEST_FILES` in `scripts/vitest-config.ts`, which is the sibling `unit-tests:obsidian-global-stubs` project on the default pool. The other remedy the advisory names, `isolate: false`, was measured and is not a trade-off worth revisiting: **91.62 s, slower than the 36.06 s baseline**, with 68 tests failing on shared state. **The shared `defineObsidianPluginVitestConfig` gives every consuming plugin the same pool** on its `unit-tests` project, with the same escape hatch as a context field, `globalStubTestFiles`, which emits a `unit-tests:global-stubs` sibling only when non-empty. Two facts measured before that shipped (2026-09-16) widen what is written above. **The locked set is four globals, not two:** listing the VM global's non-configurable own properties under `jsdom` gives `window`, `top`, `document` and `location` (the default pool locks none of them), and the one that a grep for `stubGlobal` misses is `Object.defineProperty(window, 'location', …)` — a common way to fake `location.reload`. So check a suite by running it with `--pool=vmThreads`, not by grepping it. **The VM context also LACKS globals, silently:** Vitest copies only a fixed handful of Node globals into the `jsdom` window, so `crypto.subtle`, the Web Streams classes, `CompressionStream`, the `Performance*` classes and `URLPattern` are absent under the VM pool while present under the default one. A plugin's canvas hashing failed on `crypto.subtle.digest`, and feature-detecting code would instead pass while testing a fallback Obsidian never runs. `restoreNodeWebGlobals` (`mnaoumov/typescript-test-toolkit:src/node-web-globals.ts`), called from `setup()`, defines each missing name from its Node module and leaves present ones alone. And the project's `execArgv` flag that turns off Node's Web Storage still reaches a `vmThreads` worker: `process.execArgv` carries it and Node's own `localStorage` descriptor is absent, as under `threads`. **That flag is passed only where the running Node knows it** (`process.allowedNodeEnvironmentFlags.has('--webstorage')`, the positive form, since the set never lists a `--no-` one): Node 24 rejects `--no-webstorage` in a worker with `ERR_WORKER_INVALID_EXEC_ARGV`, which failed every unit test of a plugin whose CI fell back to the LTS, and it has no `localStorage` global to turn off anyway.
  - **A per-file module realm is why `installWarningsAsErrors` marks its listener instead of comparing identity.** Under this pool each test file evaluates the module afresh while `process` stays shared per worker, so an identity check matches nothing and every file appends another `'warning'` listener until Node's `MaxListenersExceededWarning` — which that listener rethrows, failing a blameless file. Any other per-worker registration added here needs the same treatment.
- **A `unit-tests:eslint-typecheck` case timing out at 60 s is machine load, not a broken rule — retry rather than investigate.** That project runs `maxWorkers: 1` with `isolate: false` (`scripts/vitest-config.ts`) and every `@typescript-eslint/rule-tester` case builds a type-aware program, so it is the first thing in the suite to blow the per-test timeout when the box is busy — one case was measured at 141 s under load. It fails as a bare `Error: Test timed out in 60000ms.` inside `RuleTester.js` with no assertion message, which reads like a real regression. Confirm by running the named file alone (`npx vitest run <file>`): if it passes there, nothing is wrong. Do not run `find-overexposed` or another gate concurrently with `test:coverage` — that alone was enough to fail two runs on 2026-09-02, and a failed run also wipes `coverage/`, so there is no lcov left to decode afterwards.
- **`reporters` is PINNED to `['default']`, because vitest's fallback is not one reporter but two — and the one an AI session gets prints no per-file line at all.** An unset `reporters` resolves to `isAgent ? 'minimal' : 'default'`, and `std-env`'s `isAgent` is true inside every AI coding session (it reads `AI_AGENT` plus a dozen tool-specific variables). `MinimalReporter` extends the default one with `summary: false`, `silent: 'passed-only'`, and a `printTestModule` that returns early unless the module FAILED, so a passing file prints nothing at all. Measured here 2026-09-23 on `unit-tests:script-utils` (43 files, vitest 5.0.1), the same command both ways: **0 per-file lines over a 13-line log unset, 46 over a 58-line log pinned**. And `silent: 'passed-only'` also swallows a passing test's console output, so a `console.log` added to find something vanishes for a session and not for a developer. The pin lives in `DEFAULT_VITEST_REPORTERS` (`mnaoumov/typescript-dev-toolkit:src/test-runners/vitest-config.ts`, re-exported by `src/test-runners/vitest-config.ts`), is applied by `defineObsidianPluginVitestConfig` so **every consuming plugin gets it**, and is imported by `scripts/vitest-config.ts` rather than restated, since this repo's own config predates the factory. If a test log ever comes back with only totals, check this before suspecting the suite.
- **Do NOT add a reporter that names the file a dead pool worker took with it — vitest 5 does that itself.** `emitUnexpectedExit` is `(code, signal) => …` there, and builds its message from the exit code, the signal, the runner state and the files the worker held. Driven against real runs here on 2026-09-23 in all four shapes: a worker `SIGKILL`ed mid-file, one killed at import before collection, the same under `minimal`, and the realistic one — the dying file among 42 others in a parallel run, which reported `42 passed (43)` AND named the file. Under vitest 4 none of that existed, the run said only `167 passed (168)`, and a reporter reconciling the specifications `onTestRunStart` hands over against the modules that actually reported was the only way to learn which file was lost. Lifting such a reporter into this library was considered on 2026-09-23 and DROPPED on the measurement above: on vitest 5 it would be a module, a test file and a 100%-coverage burden for every consumer, carrying a claim that is no longer true.

### Consumer Script Pattern

Consumer projects import functions from `@mnaoumov/obsidian-dev-toolkit` (the Obsidian layer) and `@mnaoumov/typescript-dev-toolkit` (the generic one) and wrap them with `wrapCliTask()`:

```typescript
// scripts/build.ts
import { build } from '@mnaoumov/obsidian-dev-toolkit/bundlers/esbuild';
import { wrapCliTask } from '@mnaoumov/typescript-dev-toolkit/cli-utils';

await wrapCliTask(() => build());
```

For scripts needing argv:

```typescript
// scripts/version.ts
import {
  parseVersionArguments,
  updateVersion
} from '@mnaoumov/obsidian-dev-toolkit/version';
import { wrapCliTask } from '@mnaoumov/typescript-dev-toolkit/cli-utils';
import process from 'node:process';

const [, , ...$arguments] = process.argv;
const { options, versionUpdateType } = parseVersionArguments($arguments);
await wrapCliTask(() => updateVersion(versionUpdateType, options));
```

Config scripts re-export shared configs:

```typescript
// scripts/commitlint-config.ts
import { commitlintConfig } from '@mnaoumov/typescript-dev-toolkit/commitlint-config';

export const config = commitlintConfig;
```

The nano-staged config script calls `getNanoStagedConfig()` (not a bare re-export) so the pre-commit checks honor the `NANO_STAGED=0` `.env` opt-out:

```typescript
// scripts/nano-staged-config.ts
import { getNanoStagedConfig } from '@mnaoumov/typescript-dev-toolkit/nano-staged-config';

export const config = getNanoStagedConfig();
```

Every root config template under `templates/` (`commitlint.config.ts`, `eslint.config.mts.template`, `vitest.config.ts`, `.markdownlint-cli2.mjs`, `.nano-staged.mjs`) is a thin re-export of a matching `templates/scripts/*-config.ts`, which ships alongside it — so the copied templates resolve without hand-writing the `scripts/*-config.ts` logic file. See `templates/scripts/` for the full set of consumer examples.
